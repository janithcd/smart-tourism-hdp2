# Admin catalogue and demo booking manager setup

The tourist app contains **Manage tours**, **Manage categories**, **Manage vehicles and guides**, and **Demo bookings** screens. They use `packages`, `categories`, `services`, and `demo_bookings` in Firebase project `smart-tourism-abbb0`. They are available only to a signed-in user whose `admins/{uid}` document has `active: true` and `role: "admin"`. A menu check improves the UI; **Firestore Security Rules enforce the actual access**.

## One-time Firebase setup

1. In the Firebase Console, select **smart-tourism-abbb0** → Firestore Database → **Rules**. Compare the deployed rules with [`firestore.rules`](../firestore.rules). The file includes owner-only profiles/wishlists, active catalogue reads, admin catalogue writes, and owner-submitted demo bookings with admin review. **The `services` rule is required for the new editor and Explore; the `demo_bookings` rule is required for booking confirmation.** If your separate admin app uses other collections, preserve its required paths with equally narrow rules before publishing. The repository cannot publish rules to your Firebase project automatically.
2. Publish the reviewed rules to this project. Do not restore a time-limited `match /{document=**} { allow read, write: if ... }` rule; overlapping broad rules would defeat the admin restrictions.
3. In Authentication → Users, copy the **UID** of the account that will manage tours. In Firestore Data, create or verify `admins/{that-UID}` with fields `active` (boolean) `true` and `role` (string) `admin`. If the existing administrator document already matches that UID and fields, no new record is needed. Only a trusted Firebase Console operator or Admin SDK process should create or change this document. The Android client is forbidden from doing so.
4. Sign in as the admin. Open **Manage categories**, add a name, save it hidden, then turn on **Show category to tourists** and save again. Open **Manage tours** and choose the category from the dropdown. New tours start hidden; enter title, duration and numeric USD price, save, then turn on **Publish tour** and save again. Reopen Home/Explore to see published changes. Hiding a category or tour removes it from the public filter/catalogue without deleting its document.
5. Open **Manage vehicles and guides**. Choose Vehicle or Guide from the dropdown, enter title, duration, numeric USD rate, traveler capacity (1–30), meeting or pickup location, description, and optional HTTPS image URL. Save with **Show listing to tourists** off, then turn it on and save. Reopen Explore: the published type should use Firestore listings, while an unpublished type still shows bundled samples. Hide it again to remove it from public results. No Firebase Storage bucket is needed for an HTTPS image URL hosted elsewhere.
6. Sign in as a regular tourist. Confirm a demo booking while connected. It should appear in that account's Bookings history, and the admin should see it in **Demo bookings**. Mark it Reviewed, then remove it from the tourist's Bookings screen and refresh the admin list. Old local-only records cannot be backfilled automatically.
7. The regular tourist must not see admin menu items or other users' submissions. In the Firestore Rules Playground or emulator, tourist attempts to edit categories, packages, services, admin roles or demo review status should be denied.

If the screen says it cannot verify access, check the project ID, the signed-in UID, the `admins/{uid}` fields, the published rules and the device connection. The Firestore rules can be tested locally with Node.js 22 and Java 21 by running `npm install` and `npm run test:rules:emulator`; this uses a `demo-` emulator project and does not write to production.

The separate older admin app source is not in this repository. These submissions are simulations, not confirmed reservations. Provider registration, availability, real payment, and provider status updates remain future work. The new booking flow needs network access; previously saved local-only records remain on the same device.
